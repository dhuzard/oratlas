# Native deterministic POST supplement

This separate G1 handler program covers three previously unexercised POST methods: `/api/discuss`, `/api/federation/inbox`, and `/api/reviews/[slug]/versions/[versionId]/federation/announce`. It adds no provider mock, entropy hook, runtime write grant or shared capture-format exception. It does not complete G1 or exercise provider-backed answers, first-time federation receipt, announcement delivery or first-time announcement preparation.

`DETERMINISTIC_POST_PROGRAM` is a compiled supplemental descriptor. It declares 96 requests, 16 for each of the six existing cookie recipes. Outcomes are 14×200, 24×400, 4×401, 12×403, 6×404 and 36×409. Every principal receives a populated deterministic Discuss answer and an exact duplicate inbox receipt. EDITOR and ADMIN additionally receive the existing prepared announcement; the other principals receive native authentication/role denials. Denials are independently declared with exact native error code/message, never inferred from a golden.

## Native inputs and public scope signatures

Discuss receives the actual HMAC-signed exact canonical claim/citation/edge selection issued by `issueDiscussionTraversalScope`. The real child reissues every frozen scope through that function after closed-environment validation, and verifies it through the native signature verifier. A populated answer must contain one matched claim, linked evidence, two references, deterministic mode and `llmAvailable:false`. All bodies omit the optional `llm` configuration, the child receives no provider credentials, and attempted outbound HTTP is blocked and counted; the count must remain zero. Native deterministic mode returns before `AgentRun` persistence.

The signature is public traversal provenance, not a session or worker credential. Anonymous Explore renders these signatures (`apps/web/src/app/explore/page.tsx`); Discuss independently validates exact persisted occurrences, edges and public visibility before selecting evidence (`apps/web/src/lib/discussion-scope.ts`). A signature cannot authorize private data or activate a provider. This program preserves its exact public signed request body under the existing capture format. Session Cookie values remain absent; only their recipes and digests of actual dispatched headers are captured.

Hidden/tombstoned occurrences are real persisted canonical nodes. Their valid signatures are intentionally issued with the synthetic test key as adversarial controls; the program does not claim that Explore renders hidden data. Other controls cover modified signatures, missing versions, mismatched node/version identities, an edge whose exact target is outside the selection and invalid questions. A valid signature must not bypass public visibility checks.

The four-label integration exposed a native ordering bug: `findMany` returned the same persisted nodes in different orders, changing public scope arrays. After the existing membership and visibility checks, `validatePersistedTraversal` now returns nodes and edges in the verified canonical signed scope order. A regression varies database and submitted-array order and requires identical complete selections. Captured responses are never rewritten to hide the difference.

Inbox success is a genuine native RequestReview duplicate: its complete payload hash matches the stored immutable row, and the handler returns its existing ID, `deduplicated:true` and exact Location. Changed immutable content, a wrong target inbox and an unsupported payload fail. Announcement success uses the native accepted RequestReview and populated existing prepared AnnounceReview. The complete response payload must match the stored canonical hash; actual HTTP bytes are captured untouched, including their native property order. Pending/missing requests and a genuine hidden review version fail. Neither positive branch reaches an INSERT or audit write.

## Fixture and state evidence

The base repository-object nodes lack relational claim bindings needed for Discuss. Setup therefore used actual `materializeCanonicalReviewGraph` on three existing public/hidden/tombstoned versions in an isolated database. Its emitted 9 KnowledgeNode, 10 KnowledgeNodeVersion and 7 NodeEdge rows are frozen verbatim in `deterministic-post-fixtures.sql`. Native generated IDs and database-default timestamps are existing fixture values, never runtime replay substitutions. Explicit native compatibility updates to Review, Claim, Citation and ClaimEvidenceRelation are exported as `DETERMINISTIC_POST_FIXTURE_UPDATES`; the original HTTP program never loads this supplement. Source assertions remain source assertions, with no scientific-confirmation claim.

Load the six base fixture files, then this one supplemental SQL file under setup authority. No runtime INSERT/UPDATE grant is added. The child verifies the complete shared application-role grant closure, restricted flags, no memberships/ownership, no schema CREATE and no private-schema access. The existing app role still has its reviewed narrow mutations; this program proves it did not use them.

Every request is followed by a full-row snapshot of every permitted public table with deterministic byte ordering. All table values must equal the initial snapshot. Sidecars retain full initial/final rows, all per-request before/after digests, measured authority scope and zero outbound attempts, without label-dependent fields. Capability disclosure is refused before either evidence file is persisted. The standalone probe demonstrated two fresh restricted-role captures with identical HTTP comparisons and exact complete state. Four parent before/after captures, independent golden review and cleanup remain required; no baseline is accepted automatically.
