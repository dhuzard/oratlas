The deterministic program is an additive candidate starting after the reviewed 1165-record program on `9cb7e7534ed7560fc6bab2e002a2581a472422a1`. ## Implemented deterministic subset

Notification POST runs all six principal recipes against real handlers: own mark-read, cross-owner, missing, same-origin integrity, and repeat controls. All cross-owner checks occur before any target is read, so already-read state cannot explain a denial. The five existing remaining unread targets are marked by their owners. Repeat returns the actual 404, preserving full state and appending no audit. User cookies never confer another user's notification access.

Comment DELETE runs all six principals against missing targets, origin controls and an existing removed parent. Its author, editor and administrator receive the actual idempotent 200; ordinary nonowners receive 403, anonymous requests 401. Nonowners also deny against a still-visible target. Subsequent public exact-version reads retain populated comments and redact retained removed/tombstone canaries. This does not exercise a new visible-to-removed transition or prove its native-clock equality.

The opt-in probe first establishes the earlier program's one read notification using the real POST handler. It does not claim to execute all 1165 prior records. After every candidate request, it checks complete comment, user, notification and audit rows. Only the expected five readAt fields change to the fixed JS Date. Every denial and comment idempotent repeat preserves complete rows, including ReviewComment.updatedAt and retained body bytes. There is no new audit row, and no generated audit ID/time is excluded by this subset's checks. Sidecars contain synthetic internal fixture bodies and are not public HTTP results.

The standalone runtime role is NOINHERIT, nonsuperuser, with no role memberships or owned relations. Its only write grant is Notification.readAt; table reads are User, Notification, ReviewComment, Review, ReviewVersion, Claim, AuditEvent and RepositorySnapshot. The last SELECT was required by the real comment reader's snapshot commit lookup. It has no comment UPDATE, INSERT, DDL or credential-table grant. All database targets are isolated and synthetic, external HTTP is blocked, and the child accepts the existing closed public environment.

## Proposed fresh-removal evidence: disabled pending review

The actual removeReviewComment writes explicit JS removedAt and also triggers native Prisma ReviewComment.updatedAt. The latter is not controlled by frozen JS Date and is not among the existing reviewed state exclusions. DELETE's raw DTO has only status; public comment DTOs do not expose updatedAt. No source, response, native clock, engine or database default is modified here.

A possible bounded follow-up would compare the full row semantically: only status, removedById, removedAt and updatedAt may change; body, author, target/version and all other fields must remain exact. Status/remover/removedAt and raw public DTOs remain exact. A separate per-run sidecar retains raw before/after updatedAt and `performance.timeOrigin + performance.now()` immediately before dispatch and after completion. Observe the operation and the post-operation DB read inside that real monotonic interval. An explicit test-only skew budget, at most 1000 ms in the disconnected helper, bounds comparison with native wall time. A larger host clock step must fail, never widen the budget automatically.

The timestamp must strictly advance from the fixed original fixture and fall within the measured interval plus the reviewed skew allowance. Denial and repeat cases compare the **entire row including updatedAt exactly**, and require no audit delta. Fresh owner/editor/admin success requires exactly one attributable comment.removed audit per visible target; repeated success requires no second audit. Audit details must bind the real review slug and author-versus-editor attribution, retaining real DB transactions and restrictions.

`native-clock-observation.ts` is a disconnected proposal helper with synthetic advancing/stale/future/unchanged/invalid-window controls. It is imported only by its offline test, not by the candidate scenarios, production, capture runner or G1 acceptance. The tests show bounds sensitivity; they do not prove the caller actually measured the right interval or establish native timestamp equality. Values slightly later than the observed end can be within the explicit skew budget; “future rejection” means later than the permitted bound, not every positive offset.

Before enabling this follow-up, independently review a narrow named ReviewComment.updatedAt observational exclusion analogous to the existing explicit User.updatedAt exclusion. Keep raw values in sidecars, never rewrite a body/golden, and keep the strict native-clock equality obligation open. Such conditional semantic/clock-window evidence cannot establish exact four-run equality of native timestamps or complete G1. No new exclusion or visible-to-removed mutation is enabled by this batch.
